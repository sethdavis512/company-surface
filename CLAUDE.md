# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Company Surface is one place for every kind of company information (chats and documents today; slides, sites, and more later) and how the pieces relate, laid out as windows on a Trellis canvas. It is a copy of the Iridium template (React Router v8 SSR, Better Auth, Prisma/PostgreSQL); the template's AI chat, notes, dashboard, settings, and admin routes were removed, and their libraries and models remain unused for now.

### The surface

**Words.** The app's hierarchy is Workspace (the company) → Space → Surface (one canvas) → Cards (what sits on it: chats, documents, pull requests, charts, boards, videos, web pages, images, sticky notes, sketches). Say "card" in anything people or agents read (labels, copy, MCP tool names and descriptions). The code predates the word and keeps its own: an **item** (`SurfaceItem`, `itemId`, `items`) is a card's data, and a **window** (`ChatWindow`, `WindowControls`, `WINDOW_SIZES`, `placeWindows`) is a card as drawn on the canvas. The tickets on an issue board are **issues** (`BoardIssue`), never cards. MCP tools renamed to card names keep their old names as aliases (`OLD_TOOL_NAMES` in `app/mcp/surface-mcp.server.ts`: `list_items`, `get_item`, `link_items`, `duplicate_item`, `set_window_color`, `restack_window`); tool parameters still say `itemId`.

- Routes, all behind `authMiddleware`: `/` (`app/routes/home.tsx`) is the workspace, every space with its surfaces as tiles, plus forms to start a space or a surface (`create-space`, `create-surface`; a new surface opens at once). `/surfaces/:surfaceId` (`app/routes/surface.tsx`, 404 into its `ErrorBoundary` for unknown ids) owns the loader, left nav, and canvas for one surface, and stays mounted while its children change: the index (`surface-index.tsx`, the whole canvas, titled with the surface's name), `cards/:itemId` (`surface-item.tsx`, one card focused; 404s cards not on this surface), and `views/:viewId` (`surface-view.tsx`). Every action and link on a surface goes through `useSurfaceLinks()` (`surface-context.ts`: `action`, `item(id)`, `view(id)`, from `:surfaceId`), never a hardcoded path. `SurfaceSwitcher` atop the nav shows the space and surface and jumps to any other surface or back to all spaces. Children only set the page title; the canvas reads `itemId` with `useParams()`. Everything else is auth (`/login`, `/forgot-password`, `/reset-password`, `/logout`, `/stop-impersonating`) plus `/healthcheck` and the `/api` auth, theme, and test hooks. In development, `DEV_AUTH_BYPASS` in `app/middleware/auth.ts` lets signed-out requests through as a stand-in user (never in production or E2E).
- Data is a mock store: `app/models/surface.server.ts` keeps one shared, in-memory workspace: `spaces`, `surfaces` (each with its own `arrangement`: stack, colors, positions), `items` (every card has a `surfaceId`), `relations`, and `views` (each with a `surfaceId`). `getWorkspace()` lists spaces and surfaces; `getSurfaceForUser(user, surfaceId)` returns one surface's cards, the relations among them, its arrangement and views. A card created on its own needs a `surfaceId`; one that hangs from another (charts, PRs, attached videos, pages, images, duplicates) takes its parent's. Links and document item references stay within one surface (`linkItems` and `requireReferencesOn` refuse others). The seed has a Product space (Atlas launch, holding every seeded card, `SEED_SURFACE_ID`; and an empty Launch retro) and a Customers space (Northwind, with one document). A dev store from before spaces is replaced with the seed on the next request. The store lives on `globalThis`, so dev reloads keep it and a server restart reseeds it. Gotcha: because it outlives code reloads, a running dev server keeps a store shaped by older code, so when you add a field to `Store`, backfill it in `store()` (or reseed old shapes there, as it does for stores from before spaces) or restart the dev server, or the page crashes reading the missing field that people (through the app) and agents (through MCP) both read and write. Callers only see the `Surface` shape (`app/lib/surface.ts`) and the store's functions (`createChat`, `postMessage`, `createDocument`, `appendToDocument`, `linkItems`, ...), so a real store slots in behind them. Mutations throw `SurfaceError` for bad ids and unknown people. It is single-player: whoever is signed in is `me`. When `me` posts, the mock reply service (`pickMockReply` in `app/lib/mock-chat.ts`) answers from another participant after `MOCK_REPLY_DELAY_MS`, with `awaitingReply` true meanwhile, except in live agent chats (below).
- Live agent chats: with `ANTHROPIC_API_KEY` set (the surface loader's `liveAgent`), a chat whose only participants are `me` and the agent (`isAgentChat` in `app/lib/surface.ts`; new chats default to that) is answered by Claude (`AGENT_MODEL` in `app/agent/surface-agent.server.ts`, a Mastra `Agent` built per turn by `createSurfaceAgent`, on the AI SDK's `@ai-sdk/anthropic` model; the AI SDK tools in `surfaceTools` become Mastra tools under the same names via `asMastraTools`) instead of the mock. `AgentChatThread.tsx` sends with `useChat` to `/api/agent-chat` (`app/routes/api-agent-chat.ts`), which saves your message under the id the client shows it with (`postMessage` with `id` and `mockReply: false`), streams the reply (Mastra's stream turned into an AI SDK UI message stream with `toAISdkStream` from `@mastra/ai-sdk`, inside `createUIMessageStream`), and in `onFinish` saves it as the agent's message with its AI SDK UI `parts` (text and tool calls, in order), so the transcript and its tool cards survive reloads; history goes back to the model from those parts (`chatHistory`). The thread shows saved messages from the loader plus `useChat`'s messages the store doesn't have yet (deduped by id), and revalidates as each tool finishes so new cards land at once. Tools (`surfaceTools`) read the whole workspace (`list_spaces`, `list_cards` with a `surfaceId`, `read_card` on any card, `search` with `everywhere`; results from elsewhere name their surface and space) but make and change cards only on the chat's own surface: placed cards (documents, boards, notes, sketches) get a "made" link from the chat; charts, pages, videos, images, and PRs hang under it. Turns are limited in memory (20 a minute per person, `slideWindow`), since the surface needs no database. Workspace memory (`app/mastra/workspace-memory.ts`): Mastra schema working memory (`workspaceMemorySchema`: company, people, customers, projects, decisions, glossary) scoped to one resource, `WORKSPACE_RESOURCE_ID`, so what the agent learns in one space it knows in every space; each turn passes `memory: { thread: chatId, resource }`, and Mastra's own `updateWorkingMemory` tool shows in the chat as "Saved to workspace memory". It's working memory only (`lastMessages: false`): history still comes from the chat card, so Mastra stores no messages. It lives in the Mastra database (`MASTRA_DATABASE_URL`) and outlives store reseeds; while that database is unreachable `getWorkspaceMemory()` returns null and chats go on without memory. The seed's Playground space (`playground()` in `surface.server.ts`, backfilled into older dev stores) holds one such chat to try it.
- Agent layout: `get_layout`, `arrange_cards`, and `move_card` (MCP and the live chat agent) lay cards out on purpose. The geometry is pure and client-safe in `app/lib/arrange.ts`: `currentLayout` (saved spot, else `placeWindows`'), and `arrangeGroups`, which makes each group a column (groups left to right) or a row (groups top to bottom), carries hanging cards along under their parent as one block, leaves locked cards, and by default appends unnamed cards as a last group. The store's `arrangeCards`/`moveCard` save the spots and bump `arrangement.layoutVersion`; `useArrange` in `SurfaceCanvas` watches it and slides every card to its saved spot (Arrange's transition, then a fit), except the focused one.
- Chat windows post with a fetcher to the surface route's `action` (`action="/"`, intent `post-message`, Zod-validated), showing the message optimistically. The route polls (`usePollForChanges`, every 2s while the tab is visible) so replies and agent changes appear; `SurfaceCanvas` merges fresh loader data into its node state while rendering (`syncNodes`): existing windows keep their position and size, new items are placed right of everything (`placeNewWindow`), removed ones go.
- MCP: `/api/mcp` (`app/routes/api-mcp.ts`) is a stateless Streamable HTTP endpoint (the SDK's `WebStandardStreamableHTTPServerTransport`, JSON responses, a fresh server per request) serving the tools in `app/mcp/surface-mcp.server.ts`: items (`list_cards`, `search`, `get_card`, `list_people`, `create_chat`, `post_message`, `create_document`, `append_to_document`, `link_cards`, `create_chart`), `duplicate_card`, media (`add_video`, `add_image`, `add_web_page`, `navigate_web_page`; the web page's address is `url`, so its surface link comes back as `link`), boards (`create_board`, `create_issue`, `update_issue`), pull requests (`open_pull_request`, `set_pull_request_status`), views (`list_views`, `save_view`, `delete_view`), and arrangement (`set_card_color`, `restack_card`, and layout: `get_layout`, `arrange_cards`, `move_card`, `resize_card`). Agents write as `agent` ("Surface Agent") unless they pass `authorId`. Auth: with `MCP_API_KEY` set, requests need `Authorization: Bearer <key>`; unset, it is open in development and answers 503 in production. `.mcp.json` registers the local endpoint for Claude Code.
- Window controls (`WindowControls`, floating off each window's right edge): Focus, Bring to front, Send to back, Duplicate (`duplicateItem` via the `duplicate` intent: a copy titled "(copy)" with its own message and issue ids, the original's border color and relations, opening 48px down and right of the original's current spot, saved as its position; `syncNodes` honors a saved position for windows that arrive while the page is open; pull requests have no Duplicate, and agents use `duplicate_card`), and a border color from a six-color palette (`WINDOW_COLOR_NAMES` in `app/lib/surface.ts`, styled by `window-colors.ts` with the `--tint-*` tokens in `app/app.css`, lighter under `.dark`). Stacking order and colors are the surface's `arrangement`, saved in the store (`restackItem`, `setItemColor`; new items join the stack on top) through the route action's `restack` and `set-color` intents, so they survive reloads and are shared like everything else. `useArrangement` in `SurfaceCanvas.tsx` reads the loader's arrangement and applies changes still in flight (`useFetchers`) on top, so clicks show at once. The stack becomes each window's `zIndex`; the focused window always sits on top. A window dropped over another's top right can cover that window's controls.
- Canvas: `@sethdavis512/trellis` (published on npm from `~/repositories/trellis`; release a new version there, then bump it here, since CI and the Docker build can't clone the private repo). Its stylesheet loads through the route's `links` export. Windows are Trellis node types in `app/components/surface/`: `ChatWindow` (360x640, 9:16) and `DocumentWindow` (960x540, 16:9), which fill their node's `width`/`height` (`WINDOW_SIZES` at rest) and are placed by `placeWindows()`. Relations render as edges. Focus is URL-driven: `SurfaceNav` (left nav) and each window's Focus button (in `WindowControls`) link to `/cards/:itemId`, and `useFocusView` in `SurfaceCanvas.tsx` remembers the view, grows the focused window to fill the canvas minus `FOCUS_INSETS` (60px on top for "Back to canvas", 12px elsewhere) and frames it at zoom 1 (`focusFrame()` in `app/lib/surface.ts`), refits as the canvas resizes, and on leaving shrinks it back to `WINDOW_SIZES` and flies to the remembered view ("Back to canvas", or the browser's back button). It waits for Trellis's own readiness (`useFlowState`), since the canvas's initial fit would undo an earlier zoom. The canvas color is the `--canvas` token in `app/app.css`, a step darker than `--card`. Trellis's stylesheet is unlayered and outranks Tailwind utilities, so override its `--trellis-*` variables inline (`style`), not with classes.
- Pull requests (`PullRequestItem`, a mock: no repository behind it) are the code changes chats produce. Each has a `chatId`; `placeWindows` hangs it in a column under that chat (`pullRequestSlot`, same 360px width), new ones arriving later join that column (`syncNodes`), and its "opened" edge leaves the chat's `bottom` handle. `PullRequestWindow` links back to its chat ("From chat"), chat windows list their PRs as chips, and the footer button moves a PR along (`set-pr-status` intent: draft → open → merged). Agents open them with `open_pull_request` (which also links the chat and posts "Opened #N" there) and move them with `set_pull_request_status`.
- Filters: `FilterBar` folds to a "Filter" pill until you reach for it (hover, focus, or click opens the full bar; it folds again `CLOSE_DELAY_MS` after pointer and focus have both left), and the pill says how many filters are on and how many cards they show. It shares the canvas's top row with the Add tray (hidden while an item is focused): one full-width Trellis `Panel` (`top-left`, `right: 0`) with Add pinned left and the filter bar centered in the rest (`max-w-full`, scrolling sideways when it doesn't fit), so the two never overlap; the row is `pointer-events-none` and only the trays take clicks, so the gaps still pan the canvas. A kind and a border color combine; windows that don't match get `DIMMED` (faded, still clickable) and so do edges touching them. Filter state lives in `SurfaceCanvas` (per tab, not saved). The first fit pads 80px (`INITIAL_FIT_PADDING`) so windows start clear of the bar. Edges hide while an item is focused, because Trellis draws edge labels above every window.
- Arrange (`useArrange` in `SurfaceCanvas.tsx`) puts every window back where a fresh load would (`placeWindows`, resting sizes) and fits the view. Windows slide there because each node gets exactly one transition class at a time (`ARRANGE_TRANSITION` while arranging, `RESIZE_TRANSITION` during focus changes, `FADE_TRANSITION` otherwise): tailwind-merge keeps only one `transition-*` class, so combining them silently drops one. Dragged windows' positions are saved in the store (`arrangement.positions`, via `move-windows` from `handleNodesChange` at drag end, `moveWindows`), so they survive reloads and are shared; `toNodes` opens the tidy layout with saved windows where they were left. Arrange forgets them all (`reset-positions`, `resetWindowPositions`). Because they're shared, the Surface E2E tests run one at a time and reset positions after each (`afterEach` in `tests/surface.spec.ts`). Chat-to-PR edges have no label (the column says it, and Trellis draws labels above windows, so one would float over the cards above).
- Documents are Portable Text (`app/lib/portable-text.ts`, https://www.portabletext.org): `_type: 'block'` blocks (styles `normal`, `h2`, `h3`, `blockquote`; bullet and numbered lists with levels; `strong`/`em`/`code` decorators and `link` annotations) plus two surface types: `itemRef`, an annotation pointing a phrase at another item, and `itemEmbed`, a block of its own showing a card for one. `createDocument` and `appendToDocument` reject references to items that don't exist. `DocumentBody.tsx` renders them with `@portabletext/react` (`itemRef` as a chip linking to the item, `itemEmbed` as a card with a one-line summary; a missing item renders struck through). Agents never see Portable Text: `create_document` and `append_to_document` take Markdown (`[text](item:<id>)` for a reference, a line of `![](item:<id>)` for an embed), converted by `markdownToPortableText`, and `get_card` returns documents as `markdown` (`portableTextToMarkdown`), so agents read what they write. The seed documents are written in that Markdown too. A dev store from before Portable Text is converted in `store()` (seeded documents take the new seed's content). Kind icons and names live in `kind-icons.ts`.
- Editing documents: a focused document (`/cards/:id`) renders `DocumentEditor` (`@portabletext/editor`) instead of the read-only `DocumentBody`; on the canvas documents stay read-only, so typing never fights window drags or wheel panning. Its schema mirrors `documentBlocksSchema` in `portable-text.ts` (keep the two in step). Node registrations are at module scope (a fresh array would re-register on every keystroke); `ItemChip` and `ItemCard` take `editing` to render as text and a selectable card instead of links. `MarkdownShortcutsPlugin` turns `##`, `-`, `1.`, `>`, `**`, `*`, and `[text](url)` into formatting as you type (`item:<id>` hrefs become `itemRef`s). `EditorPickers.tsx` has two `@portabletext/plugin-typeahead-picker` pickers: `@` links an item (`insert.span` with an `itemRef` annotation, then a plain space) and `/` at the start of a block sets a style or list or embeds an item (`insert.block` of an `itemEmbed`); their popovers portal to `document.body` (the canvas is transformed, so `fixed` inside it is wrong) and are placed at the caret in a layout effect. The editor stops key events from reaching the canvas. Saving: 800ms after the last change, one save at a time, `update-document` posts the full blocks with `baseUpdatedAt`, the version it builds on (the later of the version the editor opened at and the last save's answer); `updateDocument` refuses a stale base with `SurfaceConflictError` (409) so an agent's edit is never silently overwritten, and `updatedAt` always moves forward (`nextTimestamp`). When the loader shows a newer version (an agent wrote) or a save conflicts, an alert offers "Load their version" (remounts the editor on the latest) or "Keep mine" (saves over it). Leaving the document saves what's pending at once. Gotcha: the typeahead triggers on a single typed character, so tools that insert a whole string in one input event (the in-app browser pane's `type`) never open the pickers; Playwright's `keyboard.type` and real typing do.
- Videos and web pages: `VideoItem` (a YouTube id; `youtubeVideoId()` in `app/lib/surface.ts` reads any YouTube link form, and `VideoWindow` plays it through the privacy-enhanced `youtube-nocookie.com` embed) and `WebItem` (an https address, `normalizeWebUrl()` rejects anything else, shown by `WebWindow` as a sandboxed iframe under an address bar with reload and open-in-new-tab). Typing a new address and pressing Enter posts `navigate-web` (`navigateWebPage`), so everyone sees the same page; the bar marks invalid addresses. Both can hang under a chat or document via `attachedTo` (`parentIdOf`, like charts; the seed's video hangs under the brief and its page under the Northwind doc) or sit on the main row. Their iframes take pointer events only while the window is selected or focused, so drags and wheel panning across the canvas never get caught in them. The CSP allows `frame-src https:` (`entry.server.tsx`) for these; many sites still refuse to be framed (X-Frame-Options or `frame-ancestors`), which the browser shows as a blank or error page, so the footer points at the new-tab link.
- Images and GIFs are one kind, `ImageItem` (an https `src`, `alt` text, and `animated`, which `createImage` sets from a `.gif` address via `isGifUrl` unless told otherwise). `ImageWindow` letterboxes the picture (`object-contain`, so focusing one grows it), labels animated ones "GIF" (the article reads "GIF: <title>"), and swaps a broken picture for a "couldn't be loaded" note. Images are chat-column width (360) so they hang neatly under chats; the seed hangs a photo under Launch crew and a GIF under Rosa's chat. The CSP's `img-src` allows `https:` for them.
- Search: `createSurfaceSearch(items, { nameOf })` in `app/lib/search.ts` (MiniSearch, client-safe) indexes every item (title weighted 3x, plus its text: document blocks, PR number/summary/branch, chart caption, web address, image alt) and, as entries of their own, every chat message and board issue, so a hit can name a message (`subId`, `subLabel` = sender) or issue (`subLabel` = identifier). Prefix matching, small typos for words over four letters, every query word must match; hyphenated words are indexed whole and split so "ATL-1" outranks ATL-10. It returns the best hit per item plus `itemIds` (everything that matched). Three callers: `SearchPalette.tsx` (COSS `Command`, ⌘K from `useSearchShortcut` in `surface.tsx` or the Search button atop the nav; results grouped by kind, Recent when empty; Enter flies the canvas to the window with `useZoomToWindow` from `ZoomOverlay.tsx`, or opens the item when one is focused, ⌘Enter always focuses; a message or issue hit then scrolls that row into view inside its window's own scroller via `data-message-id`/`data-issue-id` and flashes it), the filter bar (a GET `Form` with `q`, submitted on change with `replace`, read in `SurfaceCanvas` with `useSearchParams`; windows not in `itemIds` dim with the chips' dimming; All clears it; `shouldRevalidate` in `surface.tsx` skips the loader when only `q` changes), and the MCP `search` tool (same function over the store). The COSS `command` and `autocomplete` files were copied from the registry by hand because the shadcn CLI kept prompting to overwrite existing ui files.
- Left nav: `ResizableNav.tsx` lays the surface out with `react-resizable-panels` (the library Sprocket uses for its splits): a nav `Panel` 208–420px wide (`NAV_WIDTH` in `app/lib/nav-panel.ts`) that keeps its pixel width as the window resizes (`groupResizeBehavior="preserve-pixel-size"`), a `Separator` to drag (1px, with a wider invisible grab area), and the canvas filling the rest. The nav is `collapsible` to a 56px icon rail (`NavRail.tsx`: expand, a compact `SurfaceSwitcher`, search, then every saved view and card as an icon in section order, agent-made ones with a dot), by dragging it below its minimum or with the collapse/expand buttons (`useNavRail().toggle`). Width and collapsed state are saved in the `surface-nav-panel` cookie as `<width>-<0|1>` in pixels (`readNavPanel`/`serializeNavPanel`), not the library's percentages, so the loader renders your nav exactly (no jump) at any window width. Gotchas: collapsing passes through the minimum width, so `onResize` ignores widths at the minimum when remembering one; and the library only remembers the pre-collapse width within a page load, so expanding uses `resize()` to the saved width rather than `expand()`. Below `md` the nav panel and separator are hidden and the canvas fills the screen (overrides on the group's children, as Sprocket's `SplitView` does, because a `Panel`'s `className` lands on an inner element).
- Adding cards by hand: `addCard()` in the store (one entry point for every kind: starting titles like "New chat" and "Untitled document", a board key from its title's initials, a chart with sample numbers, a draft pull request; a `position` is saved for placed cards, attached ones hang from their parent) behind the surface route's `create-card` intent; a new document answers with a redirect to its card route, so it opens in the editor (`FocusOnOpen` puts the cursor in an empty one). `AddCardProvider` (`AddCard.tsx`, around the surface route's content, inside Trellis's provider) gives `useAddCard().add(kind, attachedTo?)` to three callers: the Add menu (`AddCardMenu.tsx`, "Add" in its own rounded tray at the canvas's top left; the bottom-left controls are only about the view: zoom, fit, Arrange), Add to on chat and document cards (`AddToMenu` in `WindowControls.tsx`: chart, pull request on chats, video, page, image), and the ⌘K palette's Add group (`ADD_COMMANDS` in `SearchPalette.tsx`, matched by word prefix, "add doc"). Placed cards land centered in the view below the filter bar (`viewCenter` with `TOP_PX` from `ZoomOverlay.tsx`). Videos, web pages, and images go through the provider's address dialog first, which checks the address the way the server will (`youtubeVideoId`, `normalizeWebUrl`). E2E tests for this (`tests/add-card.spec.ts`) each make their own surface over MCP so the seed stays as it is.
- Sticky notes: `NoteItem` (`text`, with `title` its first line via `noteTitle()`), 240x240, made by `createNote`/`addCard` and rewritten by `updateNote` (last writer wins), through the `update-note` intent and the MCP `add_note`/`update_note` tools. `NoteWindow` is a colored square you type straight into (a `textarea`, saved 600ms after you stop; an agent's change shows when you aren't typing). Its color is the card's palette color (`DEFAULT_NOTE_COLOR` amber until one is picked), so the color menu recolors it; `NOTE_FILLS` in `window-colors.ts` spells out the washes, painted as a tint layer (`before:`) over an opaque `bg-card`, so notes never show what's behind them.
- Right-click on empty canvas (`CanvasMenu.tsx`, COSS `context-menu` copied from the registry by hand like `command`): Add here (any kind, centered on the point you clicked, via `useAddCard().add(kind, { at })`), zoom in/out, zoom to 100%, fit, Arrange, Search. On a card or a tray (`NOT_EMPTY` selectors) it stops the event in the capture phase, so the browser's own menu shows. Double-clicking a card's `header` focuses it (`onNodeDoubleClick` in `SurfaceCanvas`), except on buttons, links, and fields inside the header (the web page's address bar). Zoomed out, the click lands on the zoom overlay first, so it zooms instead.
- Sketches (`SketchItem`, MS Paint style): strokes as vectors (`SketchStroke`: one of Paint's sixteen `SKETCH_COLORS`, a brush width, flat `[x, y, ...]` points, and `pressures` when drawn with a pen) on a `SKETCH_SIZE` 640x400 paper, so a drawing scales with its card and the zoom. `SketchWindow` has pencil, eraser (paints white, `ERASER_SCALE` wider), three `SKETCH_BRUSHES`, undo, clear, and the palette; pointer coordinates go through the SVG's `getScreenCTM()`, so canvas zoom never enters into it, and every sample the browser merged into a move is used (`getCoalescedEvents`). Ink is drawn with perfect-freehand (`strokePath` in `app/lib/sketch.ts`): each stroke is a filled outline that swells where the pointer slows and thins where it speeds up (or follows a pen's pressure), with round ends (tapers pinch closed shapes shut); the eraser (white) is an even width. Long gaps between points are filled in first (`fillGaps`), or simulated pressure reads them as very fast and draws hairlines (sparse agent strokes). Finished strokes' outlines are memoized per drawing; only the live stroke is recomputed per move. It saves the whole drawing 600ms after the last stroke (`update-sketch`, JSON checked by `sketchStrokesSchema`; `updateSketch`, last writer wins) and shows what's in flight from the fetcher's `formData`. Pure helpers (`extendStroke`, `strokePath`) live in `app/lib/sketch.ts`. Agents use `add_sketch` (optionally with strokes); the seed has a Logo doodle on Brand refresh.
- Links between cards (easy connect): the whole edge of a card is where links start, as in React Flow's easy-connect example. `LinkHandle` is a source handle styled into a ring 10px outside and 4px inside the card's border (0px inside on resizable cards, `inside={0}`, whose resize bands sit there; `clip-path` with an evenodd hole, which also limits where it can be hit, so card content and header drags are untouched); it shows faintly while you're over the card and lights up under the pointer. Drag from it onto another card (`onConnect` posts `link-cards`, label "related"; `canConnect` refuses self and duplicate links), and right-click a link or its label for "Remove link" (`unlink-cards`). Agents propose links with `link_cards` and remove them with `unlink_cards`. Links that aren't hanging ones are `floating` edges (`FloatingEdge.tsx`, geometry in `app/lib/floating-edge.ts`): each end leaves its card where the two cards face each other, recomputed from `getNodeBox` as cards move; a pair running both ways (`data.bothWays` from `toEdges`) is offset to either side (`offsetEnds`) with labels nearer their own source. Hanging links stay `smoothstep` from the parent's `bottom`. Trellis portals edge labels away from their edge, so `toEdges` wraps each label in a span carrying `data-edge-id` for `CanvasMenu` to find.
- Flowchart shapes were removed (2026-10-25): `dropRemovedKinds` in `store()` takes their cards, links, and arrangement entries out of dev stores made before then. `sizeOf()` in `app/lib/surface.ts` is the way to get a card's resting size (a resized card's saved `size`, else `WINDOW_SIZES` by kind); use it rather than `WINDOW_SIZES` wherever a card already exists. Gotcha for anything painted with palette colors: use the raw `--tint-*`/`--card`/`--ring` variables; the `--color-*` names are `@theme inline` and aren't emitted as variables.
- Deleting: the Delete button at the bottom of each card's control tray and Delete… in the header's right-click menu open a confirm modal (`DeleteCard.tsx`, `useDeleteCard().confirmDelete`) that names the cards hanging under it, which go too. `deleteItem` removes the card, everything hanging under it (`hangingUnder` in `app/lib/surface.ts`), their links, arrangement entries, saved views' framing, and issue links; documents keep mentions of deleted cards, struck through. The canvas hides them at once from the `delete-card` fetcher, and deleting the focused card goes back to the canvas first. Agents use `delete_card`.
- Resizing (chats so far): `ResizeEdges.tsx` puts a band along each edge and a square at each corner, just inside the card's border (6px and 18px on screen, counter-scaled by the zoom up to 32 flow px, `z-30` so they sit above `ZoomOverlay`), with the matching resize cursors; links start from the ring just outside (`LinkHandle inside={0}`), and the header drags the card everywhere but its top band. Drags are screen px over the zoom, through `resizeBox()` (left/top edges move the card so the opposite edges stay put) and `clampSize()` against `RESIZE_LIMITS` in `app/lib/surface.ts`: a chat goes from its resting 360x640 up to 1138x1138 (640 * 16/9 wide, as tall as that). `useCardResizing` in `SurfaceCanvas` (`ResizingContext`) resizes the node live (clearing any leftover focus transition), carries cards hanging under it along with its bottom and left edges, and on release posts `resize-card` (`resizeItem`: saves `item.size`, clamped, plus the new position when the left or top edge moved) and `move-windows` for the hanging cards. The size lives on the item, not the arrangement, so `sizeOf` (and with it `placeWindows`, `hangSlot`, Arrange, focus's shrink-back, `get_layout`, and duplicates) all use it; Arrange keeps sizes and forgets positions. `syncNodes` adopts a size changed elsewhere only for a resting node (not focused or mid-resize). The bottom right corner is focusable: arrow keys resize (Shift for 100px), one save per burst. Hidden while focused or locked. Agents use `resize_card` (MCP only; the live chat agent's tools don't have it). To make another kind resizable: add it to `RESIZE_LIMITS`, give its item type `size?`, extend `sizeOf`/`resizeItem`, and render `ResizeEdges` plus `LinkHandle inside={0}` in its window.
- Lock: the lock toggle in `WindowControls` (`set-lock`, `setItemLocked`, MCP `lock_card`) pins a card at its current spot: its node isn't `draggable`, Arrange (`useArrange`, `resetWindowPositions`) leaves it, and its position is saved. Locked ids live in the surface's `arrangement.locked`.
- Renaming: every card but a sticky note (named by its first line; `isRenamable`) shows its title through `CardTitle` (`CardTitle.tsx`). Clicking the title opens it for editing in place; so do Enter or F2 on the focused title and Rename in the header's right-click menu. Enter or blur saves (`rename-card`, `renameItem`, MCP `rename_card`, at most `TITLE_MAX` characters), Escape cancels, and the new title shows at once from the fetcher. The click waits `DOUBLE_CLICK_MS` so a double-click still focuses the card, and a press that moved (a header drag) never opens it. Which card is being renamed is `RenamingContext` state in `SurfaceCanvas`, so the menu can open it. `renameItem` leaves `updatedAt` alone: it's a document's version, and a new title shouldn't read as an agent's rewrite. `CanvasMenu` shows the card menu (Rename, Focus) for right-clicks on a card's `header` outside its controls (`HEADER_CONTROLS`); the rest of a card keeps the browser's menu.
- Leaving focus: double-click the focused card's header again, or click empty canvas (`onPaneClick`). Gotcha: React bubbles clicks from portaled popups (a card's menus and pickers) through the canvas, and Trellis reports those as pane clicks, so `handlePaneClick` ignores clicks whose DOM target isn't inside the canvas.
- Issue detail: an issue's title on a board opens it inside the board's card (`IssueDetail.tsx`, Linear style): breadcrumb back (or Escape), editable title and description, activity (who made it, then `comments`) with a comment box (⌘Enter), and properties down the right (status, priority, assignee pickers, linked cards). Edits post `edit-issue` / `move-issue` / `comment-issue` (`updateIssue` takes `title`, `description`, `assigneeId`, `null` unassigns; `commentOnIssue`); agents use `update_issue` and `comment_on_issue`. Status and priority looks are shared in `issue-looks.ts`.
- Cards that arrive while a surface is open (added by hand, by an agent, duplicated) fade and grow in: `motion-safe:animate-card-in` (keyframes in `app.css`) on every node not in `openedWith`, the ids present when the canvas mounted. It animates `opacity` and `scale`, never `transform` (which places the node) or `transition` (used by Arrange and focus).
- `placeWindows` makes each row spot as wide as its widest hanging card (a 960px web page under a 360px chat), so columns never overlap.
- Seed demo surfaces (`app/models/seed-surfaces.server.ts`): Launch retro (Product) is a developer's surface, three agent chats each with the pull request it opened (#493 to #495) and the docs page it read hanging under it, a summary document, and retro sticky notes; Brand refresh (Design space) is a designer's surface, two issue boards (DSN, AST), Wikimedia reference images, color and component pages, and notes. Image cards sit on a light mat in dark mode, so transparent diagrams stay visible.

Agent-made windows get `AgentStripe` (a bar in the `--agent` token across the top, a color kept apart from the six border tints) and `AgentBadge` in the header (`AgentMark.tsx`); nav rows get `AgentIcon`, the agent's `Avatar` is agent-colored with a bot, and the filter bar's "By agent" chip shows only agent work. `authorId` on documents is the last editor; `createdById` is who made it.
- Charts (`ChartItem`, mock numbers) are drawn with TanStack Charts (`@tanstack/charts`, its React adapter `@tanstack/charts/react`; the docs ship in `node_modules/@tanstack/charts/llms.txt`). `ChartWindow` builds a memoized `defineChart` (`barY` or `lineY`, compact band/point and linear scales), sizes the chart to its body with a ResizeObserver so it fills a focused window, and paints with app tokens (`var(--color-tint-sky)`; text and grid inherit `currentColor`), so it follows dark mode. A chart hangs under the chat or document in `attachedTo`. Hanging is generic: `parentIdOf()` (a PR's chat, a chart's parent) plus `hangSlot()` stack windows in a column under their parent, edges to hung windows leave the parent's `bottom` handle (chats and documents both have one) with no label. Agents add charts with `create_chart`.
- Arrange is a `ControlButton` in Trellis's bottom-left `Controls` (with zoom in, zoom out, fit), not a top panel: the centered filter bar is wide enough to reach the top corners on narrow canvases.
- Issue boards (`BoardItem`, a mock: nothing syncs to Linear) are one window per board, like a Linear project, on the main row (1120x540). Issues (`Issue`: identifier `KEY-n`, `ISSUE_STATUSES` backlog → done, `ISSUE_PRIORITIES`, assignee, `links` to other items, `createdById`) live inside their board. `BoardWindow` lays them out in status columns and drags them the way Sprocket's kanban does (`~/repositories/sprocket`, `KanbanBoard.tsx`): dnd-kit core only (`useDraggable` issues, each column a `useDroppable`), a grip handle per issue (`touch-action: none`, so touch drags start at once; `PointerSensor` with a 4px start distance), the other issues stay still while an issue moves, every column outlines itself as a target (2px border always, so nothing reflows), and the original fades while its copy is dragged. On top of Sprocket, which only drops at a column's top, a `DropLine` marks the exact place in the column and the issue lands there: the place comes from the dragged issue's center on screen against the other issues' midpoints (`indexAt`, read from the DOM in screen pixels, so canvas zoom never enters into it), and the drop line is zero-height with a negative margin so it never pushes issues. The keyboard sensor's coordinate getter moves the dragged issue's center onto the next drop line (up/down) or into the next column (left/right), so keyboard and pointer share one rule. `columnUnderIssue` (custom collision) picks the column under the issue's center. The dragged copy renders in a `DragOverlay` portaled to `document.body`, scaled to the zoom, with `dropAnimation={null}` (the issue is already placed from the pending fetcher, so a drop animation would fly back to the old spot first). Order within a column is the board's issue array order; `placeIssue()` in `app/lib/surface.ts` moves an issue to a status at an index, used by the store (`updateIssue` with `index`), the `move-issue` intent, and the optimistic preview. Controls inside an issue (status menu, link chips) stop key events from bubbling. The status menu still moves an issue too, and each column can file a new issue inline. Moves and new issues post `move-issue` / `create-issue` and show at once from pending fetchers (`usePendingIssues`). Merging a pull request moves issues linked to it from In Review to Done (`setPullRequestStatus`). Agents use `create_board`, `create_issue`, and `update_issue` (which takes the id or the identifier).
- Zoomed out: below `READABLE_ZOOM` (0.6), every window renders a `ZoomOverlay` (`ZoomOverlay.tsx`, added in each window component next to `WindowControls`): a transparent button over the window that shows its kind and title, centered, on hover or keyboard focus, with the text counter-scaled (`18px / zoom`) so it reads the same at any zoom, but capped at `LABEL_MAX_CQI` (11cqi, a share of the overlay's width via `@container`) so it never outgrows a narrow window. Clicking it zooms to 1 with `setViewport` from its `getNodeBox`: the window's top 12px under the filter bar (which ends 50px into the canvas) and, across, centered when it fits or 12px from the nav when it doesn't, without focusing it (no route change, no resize). So zoomed out, a click inside a window zooms to it rather than reaching its controls; dragging still moves the window. Tests that interact inside windows first call `zoomToWindow` in `tests/surface.spec.ts`.
- Saved views: `/views/:viewId` (`surface-view.tsx`, a sibling of the item route; 404s unknown ids) flies the canvas to a saved spot. A `SavedView` stores the flow point at the canvas's center plus the zoom (`viewCenter()`), not the raw offset, so it lands on the same spot at any window size. Views agents save by framing items also carry `itemIds`: each canvas then `fitView`s those windows where they actually are, at its own size (window positions live only in the browser, so the server can't frame them; `frameItems()` computes a fallback center and zoom from the default layout), and the nav shows "Fit" instead of a zoom; `useFocusView` applies it with `setCenter`, keyed on the view's numbers (so polling doesn't re-fly) and `location.key` (so picking the same view twice flies again). `SavedViews.tsx` (left nav, under Recent) saves the current spot with a name (`save-view` intent, disabled while an item is focused) and deletes (`delete-view`; deleting the open view goes to `/`), both shown at once from pending fetchers. Views live in the store with everything else; a fresh store starts with four framing related windows (`seedViews` in `surface.server.ts`).
- Recent: `useRecentItems` in `app/routes/surface.tsx` puts an item on top the moment it is opened (a deep link counts), most recent first, last `RECENT_LIMIT` = 5 via `pushRecent()`; `SurfaceNav` lists them under a Recent heading. The nav's sections (Recent, Views, each kind) reorder by dragging the grip beside each heading (dnd-kit sortable; keyboard too), and the order is saved per browser in a cookie (`app/lib/nav-order.ts` and `nav-order.server.ts`, `set-nav-order` intent), shown at once from the `nav-order` fetcher. Each section also collapses from its heading (`NavGroup.tsx`, on the COSS `Collapsible` in `app/components/ui/collapsible.tsx`); collapsed sections are saved per browser in a second cookie (`set-nav-collapsed`, the `nav-collapsed` fetcher). The panel has a 2px inset so focus rings aren't clipped by its `overflow: hidden`; Views' + button opens its section. Scroll areas use the `scrollbar-none` utility (`app/app.css`). It is in-memory route state: it survives moving between items, not a reload.
- Inside windows: put `nodrag` on anything that must not start a window drag (text, scroll areas) and `nowheel` on scroll areas (the canvas runs `scrollMode="pan"`, where the wheel pans unless the target is inside `.nowheel`).

### Two-Database Setup

The app runs two PostgreSQL instances via `docker-compose.dev.yml`:

| Database  | Port | Env Var               | Purpose                          |
| --------- | ---- | --------------------- | -------------------------------- |
| `iridium` | 5432 | `DATABASE_URL`        | Prisma (app data, auth, threads) |
| `mastra`  | 5433 | `MASTRA_DATABASE_URL` | Mastra memory and state          |

Mastra creates its own `mastra_*` tables automatically on first connection -- no migration needed. It does so the first time chat uses memory, in whatever database `MASTRA_DATABASE_URL` names, so env validation refuses a `MASTRA_DATABASE_URL` that resolves to the same database as `DATABASE_URL` (in dev too).

**Migrated from VoltAgent on 2026-10-11.** The memory database was renamed from `voltagent` to `mastra` in `docker-compose.dev.yml`, so a dev volume created before then still holds a `voltagent` database and chat answers 503 (`database "mastra" does not exist`): run `bun run docker:nuke` then `bun run docker:up`. Nothing is lost; a thread Mastra has never seen is seeded from its Prisma messages on the next turn. VoltAgent's `voltagent_memory_*` tables are never read again.

**One-time cleanup for stray VoltAgent tables:** from late February to 2026-03-24, memory was wired to `DATABASE_URL`, so an app database from that era can still hold `voltagent_memory_*` tables, which `prisma migrate dev` reports as drift. They hold no app data. Drop them from the database Prisma actually uses (`prisma db execute` reads `DATABASE_URL` through `prisma.config.ts`):

```sh
echo 'DROP TABLE IF EXISTS voltagent_memory_steps, voltagent_memory_workflow_states, voltagent_memory_messages, voltagent_memory_conversations, voltagent_memory_users CASCADE;' | bunx --bun prisma db execute --stdin
```

Or reset everything with `bun run db:fresh`.

**Gotcha: another Postgres on port 5432.** A host Postgres (Postgres.app, Homebrew) listening on `127.0.0.1`/`::1` port 5432 wins over Docker's wildcard binding, so `localhost:5432` silently reaches it, and whatever old `iridium` database it holds, instead of the `postgres` container. `lsof -nP -iTCP:5432 -sTCP:LISTEN` shows who is listening, and `SELECT version()` through `DATABASE_URL` shows which server you reached. Stop the other server, or move one of them off 5432, before trusting local migrations or E2E runs.

The ports are defaults: `docker-compose.dev.yml` publishes on `${POSTGRES_PORT:-5432}`/`${MASTRA_POSTGRES_PORT:-5433}`, and when the database URLs are unset, `prisma.config.ts` and `DEV_FALLBACKS` in `env.server.ts` follow the same vars. `tools/ports.test.ts` fails if those defaults drift. CI uses its own service containers on the defaults.

Environment variables are validated at startup by `app/lib/env.server.ts` -- missing or invalid vars produce clear error messages.

## Architecture

### Routing (config-based, NOT file-system)

Routes are defined in `app/routes.ts` using `@react-router/dev/routes` helpers (`index`, `route`, `prefix`). Route files export: `middleware` array (optional) → `loader` → `action` → `default` component.

Auto-generated types: `import type { Route } from './+types/<routeName>'`.

API routes live under `/api` prefix and export only `loader`/`action` (no component).

**React Router 8 overrides the `react-router-framework-mode` skill.** The vendored skill predates React Router 8 (its upstream, `remix-run/agent-skills`, is archived). Where it disagrees, these rules win:

- Middleware is always on. Never add `future.v8_middleware` (or any other removed `v8_*` flag) to `react-router.config.ts`; React Router 8 refuses to start with it.
- `AppLoadContext` is gone. The `context` argument to loaders, actions, and middleware is always a `RouterContextProvider`: define keys with `createContext` and use `context.set()`/`context.get()` (see `app/context.ts` and `app/middleware/auth.ts`). A custom server's `getLoadContext` must return a `RouterContextProvider`.
- Loaders and actions receive the raw incoming `request`. Use the `url` argument when you need the normalized URL (no `.data` suffix or `index`/`_routes` params).
- For anything else version-sensitive, read the version-matched docs in `node_modules/react-router/docs/` and `node_modules/react-router/CHANGELOG.md`.

### Data Access Layer

Plain async functions in `app/models/*.server.ts` — no classes, no ORM wrappers. Functions use the Prisma client directly.

- `thread.server.ts` — thread CRUD + `saveChat` (upserts last 2 messages), `searchThreads`, `updateThreadModel`, `deleteTrailingAssistantMessages`. Use `getThreadMeta` (id, owner, title, model; no messages) for ownership checks and `getThreadById` only when the messages are needed. Thread lists select no messages and are capped at `THREAD_LIST_LIMIT`
- `note.server.ts` — note CRUD with search, counts, and pagination params
- `message.server.ts` — `addMessageToThread`
- `session.server.ts` — `getUserFromSession`, `requireUser`, `requireAnonymous`, `hasRole`, `requireRole`
- `user.server.ts` — `getUserById`, `updateUserProfile`

**Soft deletes**: `Thread` and `Note` have `deletedAt`; every read in the model layer filters `deletedAt: null` and deletes set the timestamp. The model layer is the only Prisma entry point for these tables — never query them from routes directly.

### Auth Flow

- Server config: `app/lib/auth.server.ts` (Better Auth + Prisma adapter)
- Client config: `app/lib/auth.client.ts` (`createAuthClient` + `adminClient` plugin)
- API passthrough: `/api/auth/*` → `auth.handler` in `app/routes/api-auth.ts`
- Middleware: `app/middleware/auth.ts` checks session, redirects to `/login`, stores user in `userContext`
- Protect a route: `export const middleware: Route.MiddlewareFunction[] = [authMiddleware]`
- Social login: GitHub and Google via `socialProviders` in `auth.server.ts`, gated on `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` and `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`. The login loader passes `enabledSocialProviders` to `Turnstile`, which only renders buttons for configured providers
- Account flows: `/forgot-password` + `/reset-password` (token emails via `sendResetPassword`), `/settings` (profile, change password, delete account). Verification emails send on sign-up but sign-in is not gated (`requireEmailVerification` stays off — the E2E fixtures rely on sign-up auto-login)
- Admin: `/admin` (requireAdmin) lists users with search/pagination and supports role changes, ban/unban, and impersonation (`/stop-impersonating` ends it; banner renders from SiteHeader). Gotcha: the admin plugin's `adminRoles` AND its `roles` permission map must be re-keyed to the uppercase Role enum or every admin API call returns FORBIDDEN (see `auth.server.ts`)
- First admin: optional `ADMIN_EMAILS` (comma-separated). `auth.server.ts` promotes a listed user to ADMIN in `afterEmailVerification` and on each sign-in (`databaseHooks.session.create.after`), but only once `emailVerified` is true (rule in `app/lib/admin-emails.ts`); never promote at sign-up, since sign-in isn't gated on verification. The cookie cache holds the old role until the next sign-in. `prisma/seed.ts` refuses production or non-localhost databases unless `--force` (`prisma/seed-guard.ts`)

### AI Chat Flow

1. Client sends messages via `useChat` (`@ai-sdk/react`) with `DefaultChatTransport` → `/api/chat`. A normal turn sends only the newest message (`prepareSendMessagesRequest` in `thread.tsx`); regeneration sends the full history
2. Server checks the session and rate limit (20 req/min) before reading the body, rejects bodies over 1 MB (413, by `Content-Length` and while reading), validates with Zod (text parts capped at 32k chars), checks thread ownership, then streams via `agent.streamText()`
3. Mastra manages conversation memory (PostgreSQL-backed) and calls tools as needed. The agent and its memory are built on first use, not at import: `getChat()` (`app/mastra/agents.ts`) opens the Postgres store through `createLazyResource()` (`lazy-resource.ts`), so a Mastra database that is down at boot takes out chat only. A failed open is logged (`resource_open_failed`) and retried on demand with backoff (1s doubling to 30s); meanwhile `/api/chat` answers 503 with `Retry-After` (after auth and ownership checks, before touching the thread) and recovers without a restart. Never import the agent or memory at module level; call `getChat()`. A thread Mastra has never seen is seeded from its Prisma messages (text parts) before the turn, so history survives a memory reset. `/healthcheck` still reports 503 while the Mastra database is unreachable
4. `UIMessage.parts` are serialized as JSON string in the `content` DB column
5. The Mastra stream is converted with `toAISdkStream` (`@mastra/ai-sdk`) inside `createUIMessageStream`, so the client sees the normal AI SDK protocol with static `tool-<name>` parts (the thread view derives the tool name from the part type). On completion, `saveChat()` upserts messages to the database. Generation stops when the client disconnects or presses Stop (`abortSignal: request.signal`, plus a timeout), and `consumeSseStream` drains the stream server-side so an aborted turn's partial reply is still saved

Agent tools are defined in `app/mastra/tools/` (`create_note`, `list_notes`, `search_notes`, `render_card`, `get_weather`, `get_current_datetime`). The `render_card` tool demonstrates the tool-driven generative UI pattern -- the agent returns structured data and `CardToolPart` renders it as a rich visual card.

Per-thread model: `Thread.model` is set via a `set-model` intent in the `/chat` action and flows into the agent's dynamic model callback through the Mastra `RequestContext` built in `app/mastra/context.ts`, which also carries the user id that tools and the `notesContext` input processor (the notes retriever) read, so nothing user-specific is in the prompt. Regeneration (`useChat().regenerate()`) sends `trigger: 'regenerate-message'`; the server deletes trailing assistant rows, deletes the thread from Mastra memory, and resends trimmed history.

### Rate Limiting

Both limiters store state in Postgres, so limits are shared across replicas and survive deploys.

- **App limiter**: `await rateLimit({ key, maxRequests, windowMs })` in `app/lib/rate-limit.server.ts` is a sliding window over the `RateLimitBucket` table (one row per key holding the hit timestamps still inside the window). Used for chat (20/min), note creation (10/hour), and per-user write limits on notes, threads, settings, and admin actions. Each check runs in a transaction that takes a per-key `pg_advisory_xact_lock` first, so concurrent requests on any instance cannot both slip under the limit; rejected requests are not recorded. Each process sweeps expired buckets inline at most once a minute. The window math is the pure `slideWindow()`, unit-tested on its own.
- **Better Auth**: `rateLimit.storage: 'database'` in `auth.server.ts` keeps its per-IP counters in the `RateLimit` table (shape dictated by Better Auth, which also prunes it). `DISABLE_AUTH_RATE_LIMIT=true` still turns it off for E2E.

### Database pools

Every pg pool is built from `pgPoolConfig()` in `app/lib/db-pool.server.ts`: `connectionTimeoutMillis` 5s (pg's default waits forever), `statement_timeout` 15s, `idle_in_transaction_session_timeout` 30s. Sizes (`POOL_MAX`) assume 1 replica and Railway Postgres's default `max_connections` of 100 per database: Prisma 10 on the app DB, Mastra memory 5 plus a 1-connection healthcheck probe on the Mastra DB. A deploy briefly runs two replicas, so budget double (20 and 12), plus Trigger.dev workers on the app DB. Revisit `POOL_MAX` before adding replicas. `memory-storage.ts` builds the memory pg pool itself and hands it to `PostgresStore` (`{ id, pool }`), so the shared options apply; the store never closes a pool it did not create, so `close()` ends it. Every pool also needs an `'error'` listener: an idle client's error (the database restarting) is emitted on the pool and, unheard, exits the process; the memory pool gets one in `memory-storage.ts`.

### Environment Validation

`app/lib/env.server.ts` validates env with Zod at startup. Required **infra** vars (`DATABASE_URL`, `MASTRA_DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_BASE_URL`) plus **feature** keys that degrade gracefully when unset (`ANTHROPIC_API_KEY` → chat disabled, `RESEND_API_KEY` → email to console, OAuth pairs → buttons hidden, `TRIGGER_SECRET_KEY` → jobs inline, `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`/`STRIPE_PRICE_ID` → billing stub, `ADMIN_EMAILS` → no first-admin bootstrap, `MCP_API_KEY` → `/api/mcp` open in dev and off in production) and `EMAIL_FROM`, `DISABLE_AUTH_RATE_LIMIT`, `E2E_TEST_HOOKS`. Import `env` from this module instead of reading `process.env` directly in server code.

**Boot behavior is environment-dependent:** in **production**, missing/invalid vars fail fast (`process.exit(1)`) so misconfigured prod never runs. In **dev/test**, the app always boots — missing infra vars are swapped for placeholders (a console warning lists them) and missing feature keys just disable their feature. The exception is `bootEnvSchema`'s cross-field rules (a `MASTRA_DATABASE_URL` that names the `DATABASE_URL` database): no placeholder fixes a set but wrong value, so they fail boot everywhere. What's unset surfaces in a **dev-only banner** at the top of every page (`EnvBanner`, fed by `envWarnings`/`shouldShowEnvBanner` from `env.server.ts` via the root loader). The banner never renders in production or during E2E runs (gated on `E2E_TEST_HOOKS`), so it can't affect end users or test/visual snapshots.

### Billing (Stripe stub)

`app/lib/billing.server.ts` wraps Stripe behind an interface the same way `email.server.ts` wraps Resend. Without `STRIPE_SECRET_KEY` it runs in **stub mode**: `createCheckoutSession`, `createBillingPortalSession`, and `constructWebhookEvent` return mocked results logged to the console, so dev and CI need no Stripe account. Wiring the real SDK is a localized edit confined to that file (install `stripe`, fill the `TODO` branches). Persisting customer/subscription state is left to the caller (add fields to the `User` model or a `Subscription` model and update them from the webhook handler).

### Deployment

Production runs the multi-stage `Dockerfile` (Node 24 Alpine runtime). tini is the ENTRYPOINT (PID 1), and the CMD applies pending Prisma migrations (`migrate deploy`, a no-op when current) and then `exec`s node on `react-router-serve` directly (no npm or shell left in the process tree), so plain Docker hosts self-migrate on boot. Railway does not migrate on boot: the start command in `.railway/railway.ts` replaces both ENTRYPOINT and CMD (exec form, so it names `/sbin/tini` and absolute paths itself) and only serves, and migrations run once per deploy as the pre-deploy command, so a failed migration fails that deploy (the current release keeps serving) instead of crash-looping the container.

**Graceful shutdown:** in production, `entry.server.tsx` calls `installGracefulShutdown()` (`app/lib/shutdown.server.ts`). On SIGTERM/SIGINT it stops accepting connections, waits for in-flight requests (chat streams included) to finish, runs the cleanups registered with `onShutdown()`, and exits 0. Any new long-lived resource (a database pool, a client with open sockets) must register its close with `onShutdown()`, or it outlives the drain until SIGKILL. Gotcha: in a route module, call `onShutdown()` from loader/action code (see `getMastraPool()` in `routes/healthcheck.ts`), never at module top level, or the client build fails with "Server-only module referenced by client". `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=60` in `.railway/railway.ts` is the SIGTERM-to-SIGKILL window on redeploys.

**Action origins behind a proxy:** React Router's CSRF check compares the `Origin` header with `request.url`'s full origin, scheme included (since 8.3.1). react-router-serve has no `trust proxy`, so behind Railway's TLS-terminating proxy `request.url` is `http://` while browsers send `Origin: https://`, and every form and fetcher action answers 400 (the page falls to the root error boundary). `allowedActionOrigins` in `react-router.config.ts` lists the app's public hosts, from `BETTER_AUTH_BASE_URL` and `BETTER_AUTH_TRUSTED_ORIGINS` (`app/lib/action-origins.ts`). It is read at **build** time, so the Dockerfile declares both as `ARG`s (Railway passes matching service variables; plain Docker needs `--build-arg`), and changing the public domain needs a rebuild. CI's `docker` job builds with an https base URL and checks that `POST /api/theme.data` accepts the app's own https origin and rejects another. Never widen the list with `**`.

**Railway is defined as code** in `.railway/railway.ts` (IaC, evaluated by the Railway CLI via the `railway` devDependency): app service built from the Dockerfile, `Postgres` + the memory database (`memoryPostgresService` in `app.json`, `Mastra Postgres` for new copies), `/healthcheck`, `prisma migrate deploy` as the pre-deploy command, and `checkSuites: true` (Railway's Wait for CI). Per-project values live in `.railway/app.json`; the file throws if `app.json.project` doesn't match the linked Railway project. A fresh copy of the template gets its own project with `bun run provision` (`tools/provision.ts`, `provision-railway` skill), which rewrites `app.json`, runs `railway init` + `railway config apply`, generates a domain, sets secrets on stdin, and waits for `/healthcheck`. Change infra with `railway config plan` then `railway config apply`. Gotchas: variables or services omitted from the file are deleted on apply (declare externally-set values as `preserve()`), omitting `source` disconnects the GitHub repo, and databases holding data must keep their pinned image or a plan swaps the Postgres major version. Never `railway up` to production and never pass `--confirm-destructive` without the user approving the plan.

The Iridium production project is managed by `.railway/railway.ts` (applied 2026-09-25); there is no `railway.json` (Config as Code is deprecated and stops being read on 2026-12-01). `railway config plan` always shows one cosmetic diff: the planner doesn't recognize the quoted `"VoltAgent Postgres"` variable reference as unchanged, so applying it is a no-op. The production memory database keeps that service name (`memoryPostgresService` in `app.json`): renaming a service in a plan replaces it. The 2026-10-11 Mastra migration renamed only the variable it feeds, `VOLTAGENT_DATABASE_URL` to `MASTRA_DATABASE_URL`, so the next `railway config apply` adds the new variable and drops the old one.

**Production ships only by merging to `main`.** Railway's GitHub autodeploy builds the commit, and Wait for CI (`checkSuites: true` above) holds the deployment until the `CI` workflow run on that commit finishes, skipping it if CI fails. CI (`.github/workflows/ci.yml`) has no deploy job: it runs validate (typecheck, lint, format, unit), Playwright e2e, and a `docker` job that builds the production image and boots it against Postgres until `/healthcheck` returns 200. The visual inventory runs on PRs only, so it never delays or blocks a deploy. A `changes` job (dorny/paths-filter) skips unit, e2e, visual, and docker when a commit only touches `.claude/`, `.agents/`, `.specify/`, `docs/`, or markdown; validate always runs. `railway up` is not used against production.

**Deploy rules for agents.** Use the project `provision-railway` skill for first-time provisioning and for any infra change. It overrides generic Railway skills (this repo vendors none):

- Production ships only by merging to `main`; Railway builds the commit once CI passes. Never run `railway up` against production: it uploads the local working tree, uncommitted changes included, and skips git and CI.
- Infra changes go through `.railway/railway.ts` (per-project values in `.railway/app.json`): run `railway config plan`, show the user the plan, then `railway config apply`.
- Check health with `/healthcheck` and `railway logs --service <svc> --lines 100` (always pass `--lines`, or it streams forever). Roll back by reverting the commit on `main`, or with Rollback on an earlier deployment in the Railway dashboard.

### Background Jobs

Trigger.dev v4 tasks live in `trigger/` (config in `trigger.config.ts`): `send-auth-email`, `generate-thread-title`, and the scheduled `purge-soft-deleted` (hard-deletes Threads/Notes soft-deleted 30+ days ago, daily). `app/lib/jobs.server.ts` is the only enqueue entry point: with `TRIGGER_SECRET_KEY` set it hands work to Trigger.dev, otherwise it runs the same shared functions inline (`app/lib/email-jobs.server.ts`, `app/lib/thread-title.server.ts`). Keep task files thin; put logic in those shared modules so the inline fallback and the worker never diverge. `bun run trigger:dev` / `bun run trigger:deploy`; both pin the `trigger.dev` CLI to the installed `@trigger.dev/sdk` version, so bump the scripts with the SDK. CI's `trigger` job deploys the tasks on pushes to `main` once the `TRIGGER_ACCESS_TOKEN` repo secret and `TRIGGER_PROJECT_REF` repo variable exist, and is a no-op until then.

### Testing

**Unit tests** use Vitest (`bun run test`). Test files live alongside source files as `*.test.ts`. Modules that import server-side dependencies (auth, Prisma) need `vi.mock()` to avoid env validation side effects.

**E2E tests** use Playwright (`bun run test:e2e`) in `tests/`, covering auth, password reset, theme switching, CSP, healthcheck, and the surface (`tests/surface.spec.ts`: windows, their aspect ratios, the left nav, and a mock chat reply). They run against a dedicated dev server on port `7778` (override with `E2E_PORT`) so they never collide with `bun run dev` on 5173; the `webServer` config also points `BETTER_AUTH_BASE_URL` at that port and sets `DISABLE_AUTH_RATE_LIMIT=true`, `E2E_TEST_HOOKS=true` (enables `/api/test-mailbox` for reading reset links), plus a dummy `ANTHROPIC_API_KEY`.

Auth is explicit per test: the `authedPage` fixture in `tests/fixtures.ts` signs up a brand-new isolated user on demand (so parallel runs never share state), while a plain `page` stays logged out. `globalSetup` only ensures the seed users (Alice, Bob) exist for tests that log in as them. Fixtures also export `createAuthedContext` and `createFreshUser` for multi-user scenarios.

**Typing in tests:** for any field that reacts per keystroke (submits on change, opens a picker), type with `pressSequentially`, not `fill`: `fill` sets the value in one event and hides bugs that only show from the second key on (the filter-bar search once remounted its input after the first character and lost focus, and a `fill` test passed).

**Board tests** (`tests/board.spec.ts`) share one board they make over MCP and run serially, each tagging its own issues: every board widens the shared canvas, and a crowded canvas opens zoomed so far out that other specs can't click their targets. Mouse dragging is tested at a non-1 zoom (where scaling bugs show) and for a drop between two issues landing where the line shows; touch goes through the Chrome DevTools protocol (chromium only; scroll the issue into view first, raw touch events don't); keyboard presses get short pauses between keys.

**Visual inventory** (`bun run test:visual`) captures a screenshot gallery (login and the surface canvas, each in light, dark, and mobile). It lives in `tests/visual/`, runs only when `PW_VISUAL=1` enables the `visual` Playwright project (the default e2e projects ignore `tests/visual/`), and writes PNGs to `test-results/visual-inventory/` plus report attachments, so the Playwright HTML report doubles as a browsable gallery. CI runs it in its own PR-only `visual` job and uploads a `visual-inventory` artifact on every PR. Helpers in `tests/visual/helpers.ts` keep shots deterministic: `setTheme` pins the theme cookie via `/api/theme` (never leave the `system` default), `settle` waits for hydration + fonts + network idle, `createVisualContext` signs up a user with the fixed name "Visual Tester", and `snap` masks `<time>` elements (`FormattedDate` renders the current date) and disables animations. These are captures, not assertions; to add visual regression later, swap `snap()` for `expect(page).toHaveScreenshot()` and commit Linux-generated baselines.

## Conventions

### Imports

- Use `~/` path alias for all app imports (maps to `./app/*`)
- Server-only files use `.server.ts` suffix

### Components

- Use CVA from `cva.config` (not the raw `cva` package) — it integrates `tailwind-merge` — for app-authored components; copy-owned files in `app/components/ui/` keep their upstream `cn()`/`class-variance-authority` conventions
- Export both variant definitions and a named function component
- Type props with `PropsWithChildren<Props>`
- Use COSS UI primitives from `~/components/ui/` (Button, Dialog, AlertDialog, Menu, Sheet, Badge, Alert, Table, etc.). Polymorphism is `render={<Link to=... />}`, never `asChild`; menu items take `onClick`; Base UI sets `data-disabled`, so style disabled states with `data-[disabled]:`
- Semantic tokens only (`bg-background`, `bg-card`, `bg-muted`, `text-foreground`, `text-muted-foreground`, `border-border`, `text-destructive`, `bg-info/success/warning` + `-foreground`) — never raw palette classes or DaisyUI names. Tokens live in `app/app.css` on `:root` and `.dark`
- No hover-only interactive controls: anything revealed by `group-hover:`/`hover:` also needs `focus-visible:` and `pointer-coarse:` fallbacks (touchscreens never hover). COSS Buttons ship a built-in `pointer-coarse` 44px hit area; for custom controls use `pointer-coarse:` sizing utilities (e.g. `size-7 pointer-coarse:size-11`)

### Routes

- Pages set `<title>` and `<meta>` inline in JSX — no `meta` export
- Use `<Form>` with `intent` hidden fields for action disambiguation
- Export `ErrorBoundary` using `isRouteErrorResponse` for error handling
- Use `tiny-invariant` for runtime assertions

### Context & Shared Styles

- `app/context.ts` — `userContext` via React Router's `createContext<SessionUser | null>`, plus `requestIdContext`, set by the root `requestIdMiddleware` (`app/middleware/request-id.ts`), which reuses or mints `x-request-id`, echoes it on the response, and wraps the request in `withLogContext` so every `log.*` line carries `requestId`. `handleError` in `entry.server.tsx` logs loader/action/render errors the same way
- `app/shared.ts` — shared className helpers (`listItemClassName`, `navLinkClassName`)
- `app/hooks.ts` — shared hooks: `useDialogState` (controlled Base UI Dialog/AlertDialog state: `open`/`onOpenChange`/`openDialog(target?)`/`close`/`target`, with derived reopen-on-error — no setState-in-effect), `usePendingIntent`, `useIsSubmitting`

### Shared UI building blocks

Reuse these instead of re-rolling the markup: the COSS primitives in `app/components/ui/` (Dialog/AlertDialog with `useDialogState`, Button, Badge, Alert, Menu, Sheet, Table), plus the app wrappers: `SearchForm` (GET ?q= form, filters as children), `PageHeader` (h1 + action/subtitle slots), `StatTile` (dashboard stats, `data-slot="stat"`), `Spinner`, `FormAlert` (error alert, accepts action-button children; also used by ErrorBoundaries), `ToolPartShell` + `isToolLoading`/`isToolDone` (chat tool-call chrome), `FormattedDate`, `EmptyState`, `Card`, `Pagination`, `ChatBubble`. Dialog composition: `DialogHeader` outside the `<Form className="contents">`, form wraps `DialogPanel` + `DialogFooter`; Cancel is `variant="ghost"`.

### Layout

`app/root.tsx` is chrome-agnostic: it renders only the HTML document (`Layout`), the auth `loader` (`isAuthenticated`), and a bare `<Outlet/>`. All page chrome lives in per-section layout routes under `app/routes/layouts/`, composed in `routes.ts` via `layout(...)`:

- `layouts/app.tsx` — locked app shell (`h-dvh` grid: header → `main`, no footer, so the canvas fills the rest). Wraps `/` (the surface).
- `layouts/auth.tsx` — full-bleed, no header/footer. Wraps `/login`, `/forgot-password`, `/reset-password`.

Shared chrome is extracted into `SiteHeader` (`app/components/`). `SiteHeader` reads auth state via `useRouteLoaderData<typeof rootLoader>('root')` rather than props, and owns the skip link, the labeled Site/Main navs, the theme toggle (Base UI Menu), and the mobile nav Sheet. Root renders the flash `Toaster` and drives dark mode by putting `class="dark"` on `<html>` from the theme cookie; `theme === 'system'` resolves via a pre-paint inline script reading `prefers-color-scheme` (with `suppressHydrationWarning` on `<html>`). The CSP's `script-src` allows only same-origin files and a per-request nonce (no `'unsafe-inline'`): `entry.server.tsx` generates it and passes it to `ServerRouter`, React's stream, and `NonceProvider`, so any new inline `<script>` must take `nonce={useNonce()}` (`app/lib/nonce.tsx`) plus `suppressHydrationWarning`, or the browser blocks it (`tests/csp.spec.ts` checks). Gotcha: an open Sheet/Dialog makes the rest of the page inert, so tests must assert on the popup, not the trigger.

**Definite height matters:** app/auth shells use `h-dvh` (a fixed height) so the `min-h-0` + `overflow-y-auto` chain can scroll children internally. `min-h-screen` is a minimum, not a definite height, and silently breaks internal scrolling once content exceeds the viewport.

### Formatting

Prettier with: 80 char width, 4-space indentation, single quotes, semicolons, tailwindcss plugin for class sorting. ESLint with typescript-eslint and react-hooks plugin.
